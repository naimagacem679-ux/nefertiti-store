# حماية الإدارة (Cloudflare Access عبر البريد)

## ما سيُحمى — كل شيء إداري، لا صفحة اللوحة فقط
| المسار | الحماية |
|---|---|
| `/admin` (واجهة اللوحة) | Cloudflare Access |
| `/api/admin/*` (المنتجات، التصنيفات، الإعدادات، الطلبات، رفع الصور) | Cloudflare Access **+ تحقق ثانٍ داخل كل دالة** |
| `POST /api/admin/upload` | نفس ما سبق |

مسارات الزبائن العامة فقط تبقى بلا دخول: `GET /api/store` · `POST /api/orders` · `POST /api/reviews` · `GET /img/*`.

## طبقتان لا طبقة واحدة
1. **Access أمام المسارات:** يطلب بريدك ورمزاً يصل إليه. لا أحد غيرك يصل إلى الدوال الإدارية.
2. **تحقق داخل الدالة (ملف `functions/_lib/access.js`، المرحلة 2):** كل دالة تحت `/api/admin` تتحقق من ترويسة `Cf-Access-Jwt-Assertion` (توقيع الرمز + الجهة المُصدِرة + `aud`) وأن البريد داخله يساوي بريدك. لو أُزيلت قاعدة Access أو أُخطئ في إعدادها بالمستقبل، تبقى الدوال ترفض الطلب (تفشل مغلقةً).
3. إخفاء الأزرار في الواجهة ليس حماية؛ الحماية في الخادم.

## لا أسرار في الواجهة
- لا كلمات مرور ولا مفاتيح في `public/` ولا في الملفات المرفوعة إلى GitHub.
- القيم المطلوبة (`ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `OWNER_EMAIL`) ليست أسراراً بالمعنى الدقيق، لكنها توضع كمتغيرات في إعدادات Cloudflare لا في الكود. أي سرّ فعلي لاحقاً يوضع بـ `wrangler pages secret put` فقط.
- ملف `.dev.vars` للتجربة المحلية مُستثنى في `.gitignore`.

## خطوات تفعيل Access (ستتم في المرحلة الثانية مع شرح مصوَّر)
Zero Trust ← Access ← Applications ← Add ← Self-hosted ← النطاقان `/admin*` و`/api/admin*` ← سياسة Allow لبريدك فقط ← One-time PIN.
